## 2 实际接口与断言

| 阶段/角色 | 接口 | 成功依据与副作用 |
| --- | --- | --- |
| 每个VU的护理员登录 | core `GET /api/auth/csrf` → `POST /api/auth/login` → csrf → `GET /api/auth/me` | 真实CSRF/SESSION，ID和CAREGIVER角色一致；不计入稳定负载指标，不共享Cookie |
| 数据确认 | visit `GET /api/caregivers/me/schedule?dateFrom=YYYY-MM-DD&dateTo=YYYY-MM-DD` | 人工/准备阶段导出所分配visit与时间；本工具从私有fixture读取，不在每次负载中重查排班 |

## 3 数据准备与清理

### 本地复现：已提供自动隔离方案

`local_smoke.py`只对本次创建的、标记且空白的临时MySQL/Redis操作；准备4组独立护理员/老人、1主管，经过真实主管HTTP发布4计划/8次visit。4次当日签到，4次未来visit作不变对照。服务使用真实生产JAR，不加载测试身份桩，事件关闭；之后按所有权清理临时资源，确认原容器不变和端口关闭。私有日志、密码、SQL和fixture不进仓库。

### 共享测试环境：业务Owner与板块二共同确认后准备

1. 选定隔离租户/机构或专用测试库，使用合成姓名和地址、专用账号。不可将本地 `{noop}` SQL、固定用户ID或销毁临时库方式用于共享库。
2. 主管通过现有功能建立/批准护理员，建立老人、主护理员关系与已发布计划/排班。检查服务类型、技能、可用性、出行间隔及排班不重叠；需要其他板块协助的录入量在会前明确。不为凑高RPS伪造同一护理员同时服务大量不同老人。
3. 护理员查询schedule/work-pack，导出准确数字ID/版本/状态，按模板生成私有config。A可复用少量有代表性的visit；建议包含实际任务量并记录大小，不在两组实验间改动。A审计仍增长。B每个**计划到达**消耗独立合法visit，池大小≥Σceil(rps×秒数)，另留准备/人工检查余量。
4. 记录runId、账号/老人/计划/visit ID白名单、初始状态、签到窗口、新增审计时间边界、事件/队列范围和清理Owner。B的整个运行/排队与超时余量须落在合法签到窗口；不得直接SQL重置同一visit当作新交易。固定副本与HPA的B各用独立、等价的新池。
5. 小烟测先读再写1～数个新visit，人工核实状态/权限/无重复；该池从正式池排除。账号/CSRF/ID不正确立即停止。
6. 停负载后等待在途响应；对超时POST逐visit核对状态、版本、回执和事件，不能因客户端失败就假定没有写入。核对只出现白名单数据、未来对照未变、没有重复签到。
7. **共享清理不由负载工具自动执行。** 先导出去敏结果，数据Owner按白名单审阅跨库引用、审计保留和outbox/报表/通知等下游影响；正常业务“取消/停用”不等于物理删除。优先保留并标记测试记录、停用专用账号/计划；若必须删除，由Owner另提供经过评审的有序清理/恢复步骤，先备份再核对。没有跨库通用安全删除API，本包不提供一键DELETE。

B在并发和数据量未确认前只作为小规模写入验证，**首轮可先以A做HPA对照**。若团队要求“写入业务触发HPA”，必须先批准B的真实数据池和副作用预算，A结果不能替代B结果。

## 4 负载和对照设计（候选，尚未批准）

优先A：固定2个Ready副本 A0 → 同应用/资源配置、允许HPA的 A1。两组复用相同只读fixture、速率/VU/超时/阶段；审计及缓存/连接预热影响需说明。B须另备等价新池。不能同时改缓存开关、节点规格、应用版本或队列消费者后将差异归因于HPA。

联合读取模板：基线180秒×1迭代/秒；阶梯各120秒×2/4/5；维持240秒×5；停负载480秒×0。合计21分钟、2700个业务GET、上限8VU；另40次登录/预检HTTP。依据反馈WAF 2000/300秒，名义峰值1500，计入setup和发出延迟模型后约1592，其他同IP流量预算须另确认，不额外probe。这是**待容量确认的起始模板**，不是承诺这些速率会触发CPU阈值，也不是已获准施压的配置；两组及准备/复核需要分别约时间。先小烟测，不能为追曲线擅自提高速率。

本地示例故意更小，只验证脚本。HPA候选min2/max4/CPU70%来自Zhili准备分支，需重新确认实际资源/节点/入口/配置来源，不能认为已启用。CPU相对于容器requests；I/O受限时CPU不上升不能直接判HPA失败。不得用健康检查、WAF拦截或手工scale当作有效扩容负载。

## 5 指标、候选验收与停止

| 指标 | 候选判定，执行前需确认 |
| --- | --- |
| HTTP正确性 | 200且JSON和业务字段通过；HTTP与业务失败分别报告，401/403/错误身份不得当成有效吞吐 |
| p95 | work-pack成功HTTP≤1000ms；check-in成功HTTP≤2000ms；默认业务迭代≤3000ms（A可单独收紧）；同时保留全响应p95与错误率 |
| 错误率/样本 | 非预期HTTP/业务失败≤1%；逐endpoint/阶段至少100样本；不足标INSUFFICIENT_SAMPLES，不宣称SLA通过 |
| 发生器有效性 | 实际到达/HTTP数、延迟/完成数、丢弃数、stop后未调度数；正式对照要求无未解释丢弃/版本变化/漏采，检查负载机余量 |
| HPA | 板块二记录CPU/requests、desired/current/Ready、Pending/重启及配置；条件满足时观察2→N→2，N≥3且≤批准上限；只增加Pod不构成业务通过 |
| 对齐 | 工具`phases.csv`为UTC ISO8601；板块二同一时钟采集基线至缩容，保存指标自己的timestamp/window，不将采集时刻冒充指标产生时刻 |
| 数据 | 无越权/错visit/重复首次签到，B期望版本和保存状态正确；超时写入核对完成，未来对照与非白名单记录不变 |

客户端自动停止：身份/权限、重定向、非JSON、visit状态/版本不符或首次签到replayed立即停止新到达；5xx/网络错误按连续2个不重叠30秒窗口、业务迭代失败率>5%；迭代p95>5000ms按连续2个不重叠60秒窗口。每窗至少20已完成迭代；样本不足不能代替人工监控。示例区分 socketTimeoutSeconds=8、requestDeadlineSeconds=10、stopDrainSeconds=12；工作进程启动另限10秒。总 deadline/排空由监督进程触发回收，另有轮询、回收和落盘开销，不承诺配置秒数内程序已退出。不自动重试、不回滚。

人工立即停止：发现真实业务受影响、越权/错数据、Ready<2、OOM/非计划重启、容量/费用越界；Pending持续时长、RDS/Redis/连接池阈值和不可用监控的处理，由Zhili填写。板块二可要求停压；Zhili在发生器上 Ctrl+C 或写入本轮输出目录 `STOP`，关闭新请求准入，在途请求按总 deadline/共享排空期限结束并核对模糊写入。已准入请求仍可能在服务端执行，停止客户端不能撤销它。**工具不自动修改集群或恢复配置**，恢复由板块二负责。修正后另开runId重跑，不能删掉失败样本拼成一次成功实验。
